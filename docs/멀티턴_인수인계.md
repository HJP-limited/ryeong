# 멀티턴 인수인계

이 문서는 멀티턴 담당자가 **이 저장소에서 바로 작업**할 수 있도록 쓴 안내다.
코드 사본을 따로 두지 않는다 — 예전에 `handoff-multiturn/` 아래 파일을 복사해
별도 브랜치로 넘겼다가, 수정할 때마다 손으로 맞춰야 했고 금방 낡았다.
게다가 **멀티턴만 떼어내면 실행 자체가 안 된다**: `hybrid_server.py` 가
`eval_search.py` 를 임포트하고, 앱 쪽은 `CardSearchService`/`CardGazetteer` 에 붙어 있다.
그래서 경로만 가리키고 사본은 두지 않는다.

**Kotlin 이 정본이다.** `scripts/` 의 파이썬은 노트북에서 지표를 재고 눈으로 확인하는
용도이고, 실제 앱 동작은 Kotlin 코드입니다. **규칙을 바꾸면 양쪽을 같이 고치고**
`:app:testDebugUnitTest` 로 두 구현이 같은 판정을 내는지 확인해야 합니다.

### MainActivity.kt 안의 함수 위치

이 파일은 1470줄쯤 되고 UI(Compose)가 대부분이다. 멀티턴 관련은 뒤쪽에 모여 있다.
줄 번호는 바뀌므로 **함수 이름으로 찾는 게 안전하다**:

## 설계에서 지켜야 할 것

### 1. 직전 결과를 가리키는 발화는 재검색이 아니다

세 가지가 같은 원리입니다.

| 발화 | 처리 |
|---|---|
| `"그 사람들 회사 알려줘"` | `isFollowup` → 직전 카드로 다시 답 |
| `"두 번째 사람 연락처"` | `ordinalIndex` → 직전 집합의 N번째만 남김 |
| `"그중에 변호사만"` | `applyNarrowing` → 앞 턴 조건어를 질의 앞에 붙임 |

조건 누적은 **필터를 병합하지 않고 질의 앞에 조건어를 붙입니다.** 필터만 합치면 후보
풀에 그 지역 사람이 없어 걸러낼 대상 자체가 없을 수 있는데, 질의에 넣으면 검색이 실제로
데려옵니다. focus 인물을 앞에 붙이는 `resolveSearchQuery` 와 같은 방식입니다.

### 2. 생략형 후속은 두 방향이고 둘 다 처리해야 한다

한쪽만 있으면 절반이 조용히 깨집니다.

```
"주소는?"       주어 생략 + 속성 명시  →  resolveSearchQuery (focus 를 앞에)
"음가영씨는?"   주어 명시 + 속성 생략  →  carryOverAttribute (직전 속성을 뒤에)
```

### 3. `contextAnswer` 는 후속 판정 **뒤에** 와야 한다

앞에 두면 `"그 사람들 회사 알려줘"` 가 가로채여 직전 답변을 그대로 재생합니다(실측 21건).
`CONTEXT_REFERENCES` 에는 **되짚는 표현만**(아까·방금·앞서·이전·말한·찾은·기억) 넣습니다.
`"그 사람"`·`"그 회사"` 같은 대명사는 넣으면 안 됩니다 — `FOLLOWUP_PRONOUNS` 의 focus
치환이 이미 담당하고, 넣으면 `"그 사람 부서는?"` 같은 **새 질문**까지 가로챕니다.

### 4. 프롬프트에 넣지 말아야 할 것

- **작업 장부**(`pendingActions`/`resolvedActions`) — `modelView()` 가 걷어냅니다.
  넣었더니 `[current_user]` 와 같은 텍스트가 두 번 나와 2B 모델이 그대로 에코했습니다.
- **후보 개수** — `"검색 후보: 총 N명"` 을 헤더에 넣었더니 모델이 그 숫자를 **답으로 옮겨
  적었습니다**(`"디자인하는 사람 찾아줘"` → 이름 대신 `"총 3명"`). 셀 수 있는 조건일 때만
  진짜 전체 수를 넣습니다.
- **근거가 0장일 때** — LLM 을 아예 부르지 않습니다. 빈 컨텍스트를 넣으면 컨텍스트
  문자열(`"검색 후보 없음"`)을 그대로 답변으로 뱉습니다.

### 5. focus 는 narrow **이후** 목록에서 잡는다

`"오늘 날씨 어때?"` 가 카드는 제대로 비웠는데 focus 를 검색 1등으로 바꿔서, 다음
`"부서는?"` 이 엉뚱한 사람 부서를 답했습니다. Kotlin 은 `narrowByAnswer` 결과를 써서
정상이었고 **파이썬만 갈라져 있었습니다** — 양쪽 동기화를 꼭 확인하세요.

### 6. 프롬프트 규칙을 늘리지 말 것

2B 모델은 규칙이 많아질수록 준수율이 떨어집니다. 규칙 추가로 고치려던 시도는 **3번 다
실패**했고, 지금 잡힌 문제들은 전부 **결정적 코드 경로**로 해결했습니다.

## 평가 도구 사용법

```bash
# 1) 서버 먼저 (같은 저장소 루트에서)
python scripts/hybrid_server.py          # 8100
# LLM 이 필요하면 litert-lm serve --port 9379

# 2) 1~3층 — 생성 없이 라우팅/슬롯/검색만. 377턴 ~40초. 매 변경마다 돌릴 것
python scripts/eval_multiturn.py

# 3) 4~5층 — 실제 생성 + 체크리스트 + pass^k. 턴당 ~10초라 표본을 씀
#    표본은 유형별 층화 추출. **25 이상이라야 21종이 다 들어간다**
python scripts/eval_multiturn.py --generate --sample 25 --repeat 3

# 전량(377턴)을 생성 모드로 — 약 1시간. 릴리스 전에 한 번은 돌릴 것
python scripts/eval_multiturn.py --generate

# 실패 전부 보기
python scripts/eval_multiturn.py --verbose
```

### 지표 5층

| 층 | 지표 | 생성 | 뜻 |
|---|---|---|---|
| 1 | 라우팅 정확도 | 불필요 | 의도한 경로로 갔나 (search/abstain/empty_result/filtered_count/total_count/context_answer/followup/self_reference) |
| 2 | JGA + 슬롯 F1 | 불필요 | 그 턴의 **모든** 슬롯(focus + 이름/직함/지역)이 정답과 일치 |
| 3 | 턴별 R@5 | 불필요 | 정답 카드가 상위 5개에 있나 |
| 4 | 체크리스트 | 필요 | 답변에 필수 문자열이 있고 금지 문자열이 없나 |
| 5 | pass^k | 필요 | k번 다 통과한 시나리오 비율 |

**체크리스트는 LLM 이 실제로 생성한 턴에만 매깁니다.** 답변의 35%가 LLM 을 안 타는데
(카운트·기권·문맥참조·자기참조) 그 턴은 고정 문자열이라 라우팅만 맞으면 자동 통과입니다.
전체를 뭉치면 그게 숫자를 채워 어려운 턴을 가립니다.

### 시나리오

`cards_eval1000.json` 에서 **실행할 때마다 생성**합니다(seed 42 고정). 별도 데이터 파일이
없고 저장도 안 합니다 — 파일로 굳히면 데이터가 바뀔 때 낡기 때문입니다(실제로 이름을
재배정하니 손으로 만든 질문지가 통째로 무효가 된 적 있습니다).

**시나리오 130개 / 377턴, 1턴 비율 2.7%.** 멀티턴 평가이므로 다중 턴이 주가 되어야
합니다 — 처음엔 1턴이 57%였는데 그러면 이름만 멀티턴이고 실제로는 단발 검색을 잽니다.

유형 20종: 이름+생략형후속(4턴) / 6턴 장문 / 주제 전환 / 기권 후 복구 / 없는 조합 후 복구 /
카운트→좁히기 / 개념형→후속 / 동명이인 / 문맥참조 / 사실 정정 / 도구 범위 밖 / 대명사 체인 /
잡담 후 복귀 / 반복 일관성 / 본인사실 vs 명함인물 / 조건 누적 / 순서 지시 등

**6턴이 필요한 이유**: 최근 창이 4턴(`MAX_RECENT_MESSAGES=8`)이라 4턴짜리로는 롤오버가
한 번도 안 일어나 `historyDigest` 가 검증되지 않습니다.

### 표본을 쓸 때 주의

`--sample` 은 **유형별 층화 추출**입니다. 예전 균등 무작위 방식으로 `--sample 18` 을
돌렸더니 20종 중 **12종이 통째로 빠졌습니다**(문맥참조·대명사 체인·잡담 후 복귀·조건
누적·사실 정정 등). 개수가 적은 유형은 거의 확실히 탈락하고 많은 유형만 반복해서
뽑힙니다. 그러면 **지표는 1.000 이 나오는데 정작 최근 고친 것들은 한 번도 안 돌아갑니다.**

`잡담 후 복귀`(focus 오염)는 `generate_only` 라 **생성 모드에서만** 판정됩니다.
표본에서 빠지면 생성 모드를 돌리는 의미가 절반 사라집니다. 층화 추출은 이걸 항상 포함합니다.

**표본 결과를 보고할 때는 몇 종이 들어갔는지 같이 적으세요.** 전 지표 1.000 은
"이 시스템이 완벽하다"가 아니라 "표본에 든 유형은 통과했다"는 뜻입니다.

### 플래그

- `known_gap=True` — 못 하는 게 확인된 케이스. 헤드라인에서 빼고 따로 보고합니다.
  회귀망을 초록으로 유지하면서 남은 간극을 잊지 않기 위한 것입니다. **현재 0개.**
- `generate_only=True` — 답변을 봐야 판정되는 시나리오(잡담 후 focus 오염 등).
  dry-run 은 카드 정리가 안 일어나므로 건너뜁니다. 못 재는 걸 실패로 세면 지표가
  거짓말을 합니다.

## 현재 성능

```
라우팅 정확도   1.000    JGA 1.000    턴별 R@5 0.99x
체크리스트(LLM 턴) 1.000    pass^3 1.000
Kotlin 테스트 85개 통과
```

`pass^3` 측정에서 **3회 반복 실패 시나리오가 매번 동일**했습니다 — 샘플링 변동이 0이고
모든 실패가 결정적이라는 뜻입니다.

**지연 수치는 이상치를 보고 읽으세요.** 평균만 보면 끌려갑니다(실측: 평균 17.4초인데
P95 13.4초 — 174건 중 9건이 ~98초로 웜업/부하 탓). 중앙값·최댓값을 같이 찍습니다.

## 알려진 한계

- **답변의 자연스러움·말투는 안 잽니다.** 체크리스트는 문자열 포함만 봅니다(LLM 채점자
  미사용 — 짧은 사실 답변에는 규칙이 더 정확하고, 온디바이스 2B 는 채점자로 못 씁니다).
- **개념형 정답은 직함 정규식으로 근사**했습니다(`"돈 관리하는 사람"` ↔ `회계|재무|CFO|…`).
  사람이 라벨링한 게 아닙니다.
- **지연은 전부 노트북 CPU 기준**입니다.
- 6턴 시나리오가 10개뿐이라 그 구간에서 버전 비교를 하려면 더 늘려야 합니다.
  1~3층은 생성이 없어 비용이 거의 없으니 늘리기 쉽습니다.

## 에이전트 도입 시

지금 `route` 는 '우리 코드가 고른 경로'지만 도구가 여러 개가 되면 '모델이 고른 도구'로
의미가 바뀝니다. 시나리오와 정답은 **도구 중립적**으로 만들어 두었으므로 바뀌는 건 라벨
층 하나입니다. `도구 범위 밖` 유형(`"내일 3시에 일정 잡아줘"`)이 전환 지점입니다 —
지금은 "명함을 들이밀지 않는다"를 재고, 캘린더 도구가 붙으면 "그 도구로 라우팅돼야
한다"가 됩니다. **JGA·턴별 R@5·체크리스트·pass^k 는 그대로 유효**하고, 새로 필요한 건
도구 선택 정확도·인자 정확도·다중 도구 시퀀스·최종 상태 검증입니다.
