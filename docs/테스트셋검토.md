## 검색 셋

### S1. 랭킹 질의의 60%가 식별자 검색이다 — 천장의 원인

```
이름 40 · 회사명 40 · 전화 30      = 110 / 183 (60%)   R@5 전부 1.000
지역+직함 40 · 개념형 33            =  73 / 183 (40%)   ← 진짜 시험은 여기
```

BEIR·MS MARCO 같은 일반 검색 벤치에는 **식별자 검색(known-item)이 아예 없다** — 정답이 하나로
정해지고 문자열이 그대로 있으면 검색이 아니라 조회이기 때문이다. 우리 앱에서는 그게 주 용도라
빼면 안 되지만, **헤드라인 R@5 0.930은 60%의 만점에 희석된 값**이다. 유형별로 보고해야 한다
(문서에 이미 그렇게 돼 있다).

**제안:** 헤드라인에 "식별자 제외 R@5" 를 병기한다. 73질의 기준이면 0.81 근처다(개념형 0.547·0.700,
지역+직함 1.000 의 가중 평균).

### S2. 전화 질의가 현실적이지 않다

```python
frag = digits[3:]          # "01089301222" -> "89301222"
```

**하이픈 없는 8자리 중간 조각**이다. 실제 사용자는 `010-8930-1222`(전체), `8930-1222`, 뒷자리 `1222`
중 하나를 친다. 8자리 무하이픈은 그 어느 것도 아니다. 30개가 전부 이 모양이라 **한 말투만 시험**한다.

**제안:** 전체 / 하이픈 있는 뒷 8자리 / 뒷 4자리 셋으로 나눈다. 뒷 4자리는 정답이 여럿일 수 있어
(1000장 중 충돌) 진짜 랭킹 시험이 된다.

### S3. 지역+직함이 사실상 식별자다

```
'광주광역시 남구에 있는 사장 찾아줘'   정답 1장
'인천광역시 남동구에 있는 부사장 찾아줘'  정답 1장
```

**주소 수준 지역 + 정확한 직함**이라 정답이 1장으로 떨어진다. 실제 사용자는 "광주 사장" 이라고
말한다 — 그러면 정답이 여럿이고 순위가 문제가 된다. 지금 이 유형이 R@5 1.000 인 이유다.

**제안:** 시·도 수준("광주")과 직함 상위어("임원")를 섞은 변형을 절반 넣는다.

### S4. 개념형 정답 기준이 '부서'다 — 라벨을 정확히 붙여야 한다

```
'코드 짜는 직군' 정답 160장 무작위 5장:
   팀장 / 데이터플랫폼팀      CTO / 프론트엔드팀      부장 / 모바일개발팀 …
```

정답이 **부서 문자열**로 정해진다. 개발팀의 팀장·부장이 "코드 짜는 사람" 인지는 논쟁적이지만,
그 기준이 문서에 명시돼 있으면 문제없다. 지금은 암묵적이다.

이 유형에서 **R@5 는 무의미하고 R-Precision 이 맞다**는 것이 여기서 확인된다 — 정답 160장에
분모 `min(160,5)=5` 라 R@5 는 5장만 맞으면 만점이지만, R-Precision 은 상위 160장을 본다.
검색 헤드라인을 3개로 줄일 때 P@R 을 남긴 판단이 맞았다.

### S5. 기권 셋에 '그럴듯한 부재' 가 없다

```
없는 직업 10   우주비행사·등대지기·서커스 단장 …
없는 식별자 6  010-0000-0000 · zzzz@zzzz.zzz · 존재하지않는사람이름99 …
```

전부 **한눈에 가짜**다. 일반 벤치의 기권 시험은 *hard negative* — 실재할 법한데 없는 것 —
으로 만든다. 예: 코퍼스에 없는 실존풍 이름("김서준"), 실재 회사와 한 글자 다른 회사명,
실재 지역의 없는 직함 조합. 지금 셋으로는 "가짜를 가짜로 아는가" 만 보고
**"비슷한 것으로 때우지 않는가"** 는 못 본다 — 그런데 실측 실패가 정확히 후자였다
("서커스 단장" 이 우연히 정답 처리된 기록이 코드 주석에 있다).

**제안:** 멀티턴 v1.2 에 넣은 `absent` 생성 방식(실존 성 + 흔한 이름, 코퍼스에 없는 것만)을
검색 셋에도 10개 넣는다.

### S6. 코퍼스가 너무 깨끗하다

```
1000장 · 고유 이름 984 · 고유 회사 892 · 고유 직함 87 · industry 채워진 카드 60(6%)
```

실제 연락처는 같은 회사 사람이 여럿이고, 동명이인이 있고, 비슷한 회사명이 있다. 우리 코퍼스는
회사 892종이라 **회사명 검색이 곧 1인 조회**다. 식별자 검색이 1.000 인 이유의 절반은 여기다.
`industry` 는 94% 비어 있어 개념형 질의에 쓸 수 없다.

이건 시험지가 아니라 **데이터의 한계**다. 1000장 온디바이스 연락처로는 현실적인 규모이지만,
"같은 회사 5명 중 한 명 고르기" 같은 시험은 이 데이터로 못 만든다.

## 멀티턴 벤치 v1.2

### M1. 방해 턴이 전부 같은 모양이다 — 가장 큰 구조 한계

```
방해 턴 718개 중 718개 = "X씨 [칸] 알려줘"
```

실제 대화의 방해는 다르다: 개수 질문("대전에 몇 명?"), 목록("판교 개발자 찾아줘" → 5명),
잡담("고마워"), 좁히기("그중에"). 이것들은 **focus 를 흐트러뜨리는 방식이 제각각**이라 진짜
방해가 된다. 지금 방해 턴은 focus 를 한 사람에서 다른 한 사람으로 옮길 뿐이다.

절제 실험에서 이름 명시 질문이 재작성 없이도 27/27 이었던 것도 이와 관련 있다 — 방해가
약해서 "긴 대화" 가 실제로는 어렵지 않다.

**제안:** 방해 턴 풀에 개수·목록·잡담을 넣는다. 단, 그러면 **정답 카드 집합이 바뀌지 않도록**
(목록 질문의 결과에 대상이 섞이지 않게) 검사기에 가드레일을 추가해야 한다.

### M2. 발화 틀이 62종뿐이다

```
918턴 · 서로 다른 틀 62개 · 채점 턴 200개 · 틀 61개
```

QuAC·CoQA 는 사람이 쓴 문장이다. 우리는 템플릿이라 **모델이 패턴을 외울 수 있다.**
동결본이라 버전 간 비교는 성립하지만, "이 틀에서만 되는가" 는 못 가린다.

**완화책은 이미 있다:** 생성 회귀셋(`eval_multiturn.py`)이 발화 풀 123틀을 쓴다. 두 셋의
결과가 갈리면 틀 의존을 의심한다.

### M3. 참조 분포가 적대적이다 — 그대로 두되 명시한다

```
정정 55 (27%) · 대명사 47 · 이름 49 · 순서 지시 36 (18%) · 없는 사람 13
```

실제 사용자가 "맨 처음 물어본 사람" 을 5번에 1번 말하지는 않는다. 이건 **어려운 것을 일부러
많이 넣은 적대 분포**이고, 그 목적(천장 깨기)에는 맞다. 다만 **"사용 분포 기준 정확도" 로
읽으면 안 된다.** 발표 때 이 점을 붙인다.

### M4. 범위가 '1인 조회' 로 좁다 — 생성 회귀셋과의 분업

벤치에는 복수 결과·좁히기·개수·잡담 복귀가 **없다.** 시나리오당 채점 턴 1개 구조가
집단 검색과 안 맞아서 뺐고, 그것들은 생성 회귀셋 27유형이 맡는다.

```
동결 벤치        1인 조회의 대화 참조 해소     시간에 걸친 비교
생성 회귀셋      집단·개수·좁히기·잡담 27유형   버전 안 회귀 탐지
```

둘 다 돌려야 전체가 보인다. 하나만 인용하면 안 된다.

### M5. 이름 명시(named)는 전부 거리 0 이다

```
named 49개 중 거리 0: 49개
```

"16턴 뒤에 이름 대고 새로 묻기" 는 문맥 참조가 없어 난이도 L1 이 맞다. 긴 대화 뒤에도
새 질문이 되는지를 보는 **회귀용**이고, 그렇게 쓰면 된다.

### M6. L4 의 점수 폭이 넓다

```
L4 38개: 점수 6 ~ 15
```

6점과 15점이 같은 칸이다. 지금은 n 이 작아 나누면 칸당 n<10 이 된다. 규모를 300 이상으로
올릴 때 **L5(≥10)** 를 분리한다.

### M7. 답 없는 문제의 칸 분포

```
부서 21 · 회사 9 · 주소 7 · 직급 6 · 이메일 4 · 전화 0
```

데이터의 빈 칸 비율(부서 25.6%·주소 10%·회사 7%)을 따라간다. 전화는 빈 카드가 **0장**이라
"있는 사람의 없는 전화" 는 만들 수 없고, `absent`(없는 사람)로만 시험한다. 이건 데이터 사실이다.

### M8. 홀드아웃 층화 — 통과

```
공개  A/L1 6 · A/L2 22 · B/L3 23 · C/L3 36 · D/L4 34 …
홀드  모든 칸 3~4
```

칸별로 고르게 뗐다. 다만 **공개셋 칸 중 n<10 이 여섯 개**(B/L1 2, D/L1 3 …)라 칸 단위 비교는
못 한다. 행·열 합계만 쓴다 — `run_bench.py` 가 n<20 이면 경고를 찍는다.

**여기서 통과한 것은 '층화' 뿐이다.** 이 홀드아웃은 같은 카드 · 같은 생성기 · 같은 표현
템플릿 · 같은 시드에서 만든 뒤 **시나리오 id 만 나눈 것**이고, 정답과 문장이 같은 JSON 에
평문으로 들어 있다. 실행 결과도 `bench/runs/` 에 남는다. 즉 **독립 수집이 아니므로 일반화
근거로 쓸 수 없다** — 증명되는 것은 "같은 분포에서 아직 패치하지 않은 몫도 통과했다" 까지다.
일반화를 재려면 생성기와 분리된 블라인드 셋이 따로 있어야 한다.

## 표준 벤치와의 대응

| 표준 | 무엇 | 우리와의 관계 |
|---|---|---|
| **QuAC** | 대화형 QA. 대명사 해소, 답 없음 ~20%, 평균 7턴 | **가장 가깝다.** 우리 벤치 구조(참조 해소 + 답 없음 30% + 깊이 1~16)가 이 모양 |
| MultiWOZ | 대화 상태 추적. JGA | JGA 를 여기서 빌렸다. 우리는 슬롯이 2개(focus·field)라 훨씬 단순 |
| BEIR | 주제 검색 13~18셋. nDCG@10 | 개념형 33질의가 이 종류. 나머지 170은 BEIR 에 없는 유형 |
| MS MARCO | 실제 질의, 정답 1개 위주. MRR@10 | 식별자 검색 110질의가 이 모양. 단 MARCO 는 사람이 쓴 질의 |
| MT-Bench | 2턴, LLM 판정 | 비교 불가 — 우리는 결정적 채점, 최대 16턴 |

**일반 벤치의 난이도 수준:** MultiWOZ JGA 0.5~0.6, BEIR nDCG 0.4~0.5, QuAC F1 0.6~0.7.
우리 v1.1 은 1.000 이었다. v1.2 목표 0.7~0.85 는 이 범위에 맞춘 것이다.

| 4 | **S2·S3** 전화·지역 질의 말투 다양화 | 작음 | 한 말투만 되는 것을 "된다" 고 말하지 않게 |
| 5 | M2·M3·M6 | 문서화만 | 오독 방지 |

동명이인을 일부러 넣어야 한다.
