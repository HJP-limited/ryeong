# HJP 명함 검색 구조

온디바이스(폰 안에서 동작) 명함 검색·조회 파이프라인.

---

## 1. 전체 흐름

```
질의  "경기도에 있는 상무 찾아줘"
  │
  ├─① 키워드 검색  →  글자가 겹치는 카드
  ├─② 시맨틱 검색  →  의미가 비슷한 카드
  │
  ├─③ RRF 융합     →  두 순위를 합쳐 후보 추림
  ├─④ 필드 조건    →  조건에 맞는 카드만 남김
  ├─⑤ 기권 게이트  →  근거가 없으면 아예 포기
  │
  ├─⑥ 상위 5명을 LLM(Gemma)에게  →  답변 생성
  └─⑦ 답변 후처리  →  답변에 맞게 화면 카드 정리
```

**①과 ②는 성격이 정반대라 서로 보완한다.**

| | 키워드 검색 | 시맨틱 검색 |
|---|---|---|
| 방식 | 글자가 겹치는지 (FTS4 전문검색) | 문장을 벡터로 바꿔 의미 유사도 |
| 강함 | `010-1234`, `김철수`, `삼성전자` | "돈 관리하는 사람" → 회계사·CFO |
| 약함 | "돈 관리하는 사람" (글자가 안 겹침) | 전화번호 (숫자에 의미가 없음) |

**③ RRF 융합**: 두 검색의 *순위*를 합친다. 점수 단위가 달라 직접 더할 수 없으므로
"몇 등이냐"만으로 합산한다 — `1/(60+등수)`.

## 2. 필드 조건 — 이름 · 지역 · 직함

### 하는 일

질의에서 **데이터에 실제로 존재하는 값**을 뽑아 조건으로 쓴다.

```
"경기도에 있는 상무 찾아줘"
   경기도 → 데이터에 있는 지역   ✓ 조건 채택
   상무   → 데이터에 있는 직함   ✓ 조건 채택
```

### 왜 필요한가

검색은 점수로 줄 세울 뿐, **"두 조건을 동시에 만족하는가"**는 못 본다.
융합 결과에는 "경기도지만 상무가 아닌 사람", "상무지만 경기도가 아닌 사람"이 섞인다.

**측정** (정답: 경기도 AND 상무 = 6명)

| 조건 | 후보 수 | 그중 정답 | 정답률 |
|---|---|---|---|
| 지역만 | 172명 | 6명 | **3.5%** |
| 지역 + 직함 | 6명 | 6명 | **100%** |

후보가 그대로 LLM에게 넘어가므로, **후보가 깨끗하면 소형 모델이 실수할 여지가 사라진다.**
(2B 모델은 후보가 섞이면 개수를 잘못 세거나 무관한 사람을 답한다)

### 어휘는 자동 추출된다

사람이 단어를 적어 넣는 게 아니라 **카드 데이터를 훑어서 모은다.**

```
카드 1000장 → 이름 984종 / 지역 42종 / 직함 87종 / 회사 889종 / 부서 67종
```

카드가 바뀌면 어휘도 자동으로 따라간다. 새 회사·직함이 들어와도 코드를 안 고쳐도 된다.

### 판정 순서: 이름 → 직함 → 지역

직함을 지역보다 **먼저** 본다. `상무`는 직함이면서 광주 `상무대로`의 일부이기도 한데,
지역으로 새면 "주소에 상무가 들어간 사람"만 남아 진짜 상무가 전부 잘린다.

### 적용 방식은 조건마다 다르다

| 조건 | 방식 | 이유 |
|---|---|---|
| 이름 | 하드 필터 | 정확히 한 사람을 지목한 것 |
| 지역 | 하드 필터 | 명확한 소속 조건 |
| 직함 **+ 다른 조건** | 하드 필터 | 위 표의 3.5% → 100% |
| 직함 **단독** | **정렬만** (삭제 안 함) | 아래 참고 |

**직함 단독일 때 정렬만 하는 이유**
- 하드 필터를 걸면 → 시맨틱이 찾아낸 유사 직함(`고문변호사`)이 잘린다
- 아무것도 안 하면 → 융합이 `고문변호사`를 진짜 `변호사`보다 위에 올린다
- **정렬**은 정확 일치를 앞에 두면서 유사 직함을 뒤에 남겨 둘 다 해결한다

**복합 조건에서 결과가 0명이면 그대로 기권한다.** 없는 조합에는 없다고 답하는 게 맞다.

> 예전에는 이때 직함 조건만 떼고 다시 찾는 '완화'가 있었다. 측정해 보니 **평가 203질의에서
> 한 번도 발동하지 않았다** — 질의가 데이터에 실제로 있는 조합으로 만들어지기 때문이다.
> 지표는 하나도 떠받치지 못하면서, 사용자가 **없는 조합**을 물을 때만 발동해 거짓 답을 만들었다:
> "판교에 있는 디자이너" → 판교에 디자인 계열이 0명인데 직함을 떼고 판교 9명을 넘겨서,
> LLM이 그중 **주임 한 명을 디자이너라고** 답했다. 규칙을 지우니 지표는 소수점까지 그대로였고
> 그 질의는 기권으로 바뀌었다.

## 3. 기권 — 없는 걸 물으면 아무것도 안 준다

| 종류 | 예시 | 판정 근거 |
|---|---|---|
| 없는 지역 | "세종특별자치시 디자이너" | 그 지역이 데이터에 없음 |
| 없는 이름 | "정하은씨 어디서 만났더라" | 명단에 없음 |
| 매칭 없는 식별자 | "010-0000-0000" | 그런 번호 없음 |

### 왜 필요한가

기권이 없으면 **시맨틱이 억지로 비슷한 사람을 끌어오고, LLM이 그 사람으로 답을 지어낸다.**

### 핵심 원칙 — '값의 부재'로만 판단한다

```
✅  "질의가 특정 값을 지목했는데 그 값이 데이터에 없다"   → 검증 가능
❌  "점수가 낮다 / 매칭이 적다"                        → 개념형 질의와 구분 불가
```

점수로는 가를 수 없다는 게 측정으로 확인됐다:
`"백령도"`(정답 0명) 유사도 **0.423** > `"공무원 직급"`(정답 31명) 유사도 **0.280**.

## 4. 라우팅 — 못 하는 축은 뺀다

**전화번호·이메일 질의는 시맨틱 축을 융합에서 제외한다.**

숫자는 의미가 없어 시맨틱이 전혀 못 찾는데(R@5 = 0.000), 대등하게 섞으면
좋은 키워드 결과를 밀어낸다.

```
"010-3030-6030"   시맨틱 포함  P@5 = 0.233
                  시맨틱 제외  P@5 = 1.000
```

## 5. 결정적 우회 — 코드가 먼저 가로챈다

**검색·LLM을 아예 안 태우고 코드가 즉시 답하는 4가지.**

| 종류 | 예시 | 우회하는 이유 |
|---|---|---|
| 자기참조 | "너는 누구야?" | 검색에 태우면 "너"를 명함 속 인물로 오인 |
| 전체 개수 | "전체 몇 장이야?" | 검색은 top-5까지만 채워서 1000장인데 "총 5명"이 됨 |
| 조건 카운트 | "상무 몇 명이야?" | 〃 (실제 41명). 전체를 직접 세서 답한다 |
| 빈 질문 | `""` | 파이프라인을 다 돌고 되묻는 답을 만들어냄 |

### 설계 원칙

**"모델에게 시키지 말고, 코드가 먼저 가로챈다."**

온디바이스 2B 모델은 프롬프트 규칙이 늘수록 준수율이 떨어진다. 규칙으로 시키는 대신
판정이 확실한 질의는 코드가 직접 처리한다.

**부수 효과**: 카운트 질의가 **0.1초** (LLM을 안 부르므로. 검색 경로는 10초 안팎)

## 6. 답변 후처리 — 답변과 카드를 일치시킨다

검색은 top-5를 채우느라 무관한 후보를 함께 담는다. LLM 답변을 보고 **화면에 띄울 카드**를 정한다.

| 순서 | 조건 | 처리 |
|---|---|---|
| 1 | 거절 문구가 있음 | 카드 전부 비움 |
| 2 | `총 0명` | 카드 비움 (숫자로 표현된 거절) |
| 3 | 답변이 어떤 카드를 **근거로 삼음** | 그 카드만 남김 |
| 4 | **이름 조건으로 후보가 1명** | 그대로 남김 |
| 5 | `총 N명` (N < 후보 수) | 상위 N개만 남김 |
| 6 | 위 어디에도 안 걸림 | 카드 비움 (명함과 무관한 답변) |

### 3단계 '근거' 판정

이름뿐 아니라 **회사 · 주소 · 이메일 · 전화 뒷자리**도 근거로 인정한다.
필드 값으로만 답하는 게 정상인 질문이 많기 때문이다.

```
"문선영씨 회사가 어디야?"  →  "주식회사 노블어패럴입니다."
                              ↑ 이름은 없지만 회사명이 그 카드의 값이므로 근거로 인정
```

주소는 LLM이 괄호를 생략하는 일이 잦아 앞부분 일치도 허용한다.

### 4단계 — 후보가 하나면 고를 게 없다

이 단계가 하는 일은 '후보 여럿 중 답변이 가리키는 사람 고르기'다. 이름으로 한 사람이 이미
특정됐다면 고를 대상이 없으므로 답변이 그 카드를 다시 인용하지 않아도 남긴다.

```
"손다은씨 회사가 어디야?" → "(주) 블루오션컨설팅입니다."   카드 1장
"주소는?"                 → "전라남도 순천시 월드컵로 11"   카드 1장
"직급은?"                 → "AI 개발자"                    ← 3단계에 안 걸림
"부서는?"                 → "데이터사이언스팀"              ← 3단계에 안 걸림
```

이 규칙이 없을 때 아래 두 줄은 **카드가 매 턴 사라졌다.** 답이 짧은 필드 값이라
이름·회사·주소가 하나도 안 들어가기 때문이다.

경계는 테스트로 고정했다 — **동명이인 2명**이면 예전대로 비우고(누구인지 안 가려짐),
**이름 조건 없이** 우연히 1명이 남은 경우도 비운다("오늘 날씨 어때?"에 엉뚱한 명함 방어).

## 7. 멀티턴

- **최근 4턴(메시지 8개)** 은 원문 그대로, 그보다 오래된 대화는 요약본으로 압축
- 요약은 **모델 호출 없이** 결정적으로 압축한다(온디바이스 지연 유지)
- **생략형 후속**: "주소는?", "전화번호 뒤 4자리는 뭐야" 처럼 속성 명사로 시작하면
  직전 인물을 앞에 붙여 검색한다
- 단, `\d{3,}`(연속 3자리 이상 숫자)이 있으면 새 검색값으로 보고 붙이지 않는다
  (`4자리`는 자릿수 표현, `4312`는 검색값)

## 8. 현재 성능

`python scripts/eval_search.py` — 질의 205개, 앱에 실제로 들어가는 데이터 1000장,
앱과 동일한 키워드 랭커.

| 지표 | 값 |
|---|---|
| R@5 (재현율) | 0.930 |
| **P@R (정밀도)** | **0.880** |
| MRR (첫 정답 순위) | 0.926 |
| nDCG@5 (순위 품질) | 0.911 |
| 기권 정확도 | 7/20 |

| 질의 유형 | R@5 | P@R |
|---|---|---|
| 전화 · 회사명 · 이름 | 1.000 | **1.000** |
| 지역+직함 | 1.000 | **0.850** |
| 개념형 (쉬움) | 0.700 | 0.600 |
| 개념형 (어려움) | 0.547 | **0.456** |

### 지표 읽는 법

- **R (Recall, 재현율)** = 정답 중 몇 %를 찾았나 → *놓친 게 없나*
- **P (Precision, 정밀도)** = 보여준 것 중 몇 %가 정답인가 → *노이즈가 없나*
- **@5** = 상위 5개 기준 / **@R** = 정답 개수만큼만 보고 계산

> **P@5로 유형을 비교하면 안 된다.** 정답이 1명인 질의는 상위 5개 중 4개가 무조건 오답이라
> P@5가 0.2를 넘을 수 없다. 회사명 유형의 P@5 0.210은 **이론적 최댓값**이며 P@R은 1.000이다.

## 9. 남은 약점

### 개념형 (P@R 0.456) — 임베딩 모델의 한계

실패 질의를 단계별로 추적하면 **100%가 '순위 밀림'** 이다.

```
'코드 짜는 직군 찾아줘'   정답 순위 [1, 2, 4, 5, 7, ...]  ← 3위·6위에 오답이 끼어듦
'UI 만드는 사람 찾아줘'   정답 순위 [2, 3, 5, 7, ...]     ← 1위·4위가 오답
```

정답을 **못 찾는 게 아니라**(후보 풀에 다 있음) 시맨틱이 정답과 오답을 충분히 못 가른다.
그래서 융합 파라미터를 아무리 조정해도 안 움직인다(RRF_K 10~100 전 구간, 시맨틱 가중
1.5~3.0 모두 ±0.002). 임베딩 모델 성능에 직결된 문제다.

현재 EmbeddingGemma 300M 을 쓰는데, **온디바이스 + LiteRT 변환 + 한국어 + 300M급**을
동시에 만족하는 대안이 마땅치 않아 유지한다. 질의 임베딩은 폰에서 실시간으로 돌아야 해서
모델 크기가 곧 앱 용량·메모리·지연이다.

### 기권 (7/20) — 개념형과 같은 뿌리

```
"우주비행사 찾아줘"       정답 0명    ← 기권해야 함
"소프트웨어 만드는 사람"   정답 122명  ← 답해야 함

둘 다 키워드 매칭 0건, 시맨틱 신호도 겹침 → 검색기가 구분할 방법이 없다
```

### "판교에 있는 개발자" — 병목은 검색이 아니다

판교에는 `Senior Engineer`·`Principal Engineer`·`Data Scientist`가 있는데
`개발자`라는 단어와 정확히 일치하지 않아 기권한다. 검색을 고치면 될 것 같지만 아니다.

직함을 정렬로 바꿔 시맨틱이 살아남게 해 보면 **검색은 이들을 상위로 제대로 올린다.**
그런데 Gemma가 **"총 0명"** 이라고 답한다 — 2B 모델이 Data Scientist를 개발자로 인정하지
않는다. 반대로 "판교에 있는 디자이너"에는 후보 1위인 **주임을 디자이너라고** 답한다.

즉 병목은 답변 모델의 판단이고, 필터·정렬 어느 쪽으로도 못 고친다.
게다가 정렬로 바꾸면 결과 집합이 무너져(지역+직함 Full P 0.578 → 0.017)
"경기도에 상무 몇 명?"이 경기도 사람 전원을 답으로 낸다.
**순위와 집합은 다른 요구다** — 개수나 카드 목록이 답인 질문에는 필터가 필요하다.

틀린 답보다 기권이 낫다는 기준에 따라 현재 동작을 둔다.

### 그 외

- **성씨 단독 검색 미지원** — "황씨 몇 명?" 은 전체 이름만 어휘로 갖고 있어 정확히 못 센다
- **합성 직함** — `고문변호사`는 띄어쓰기가 없어 `변호사` 단어 매칭에 안 걸린다.
  그래서 카운트(65명)와 시맨틱 검색의 기준이 달라 보인다 — 카운트는 토큰 정확일치라
  `고문변호사` 29명이 빠지지만, 시맨틱은 유사 직함으로 잡아낸다.
  (데이터 표기 정규화가 맞는 해법)
- **개념형 답변 형식이 일정하지 않다** — `소송 맡길 사람` → "총 3명"(가짜 총계),
  `코드 짜는 사람` → 1명만, `돈 관리하는 사람` → 이름 5개. 프롬프트 영역인데
  규칙 추가는 2B 모델에서 3번 다 실패했다(늘리면 준수율이 떨어진다).
